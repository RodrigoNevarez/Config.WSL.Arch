#+TITLE: Use WSL-native npm instead of Windows npm
#+DATE: 2026-08-12

* Problem

Inside the Arch WSL shell, =npm= resolves to the Windows install via
interop instead of the nvm-managed WSL npm:

#+begin_src sh
[root@rodris arch]# which npm
/mnt/c/Program Files/nodejs/npm
#+end_src

This happens because WSL's interop PATH (=/mnt/c/...=) is ahead of the
nvm path, or nvm isn't loaded in the shell at all. As a result, global
npm installs (e.g. =claude-code=) land in the Windows npm prefix
(=C:\Users\rodri\AppData\Roaming\npm=) instead of inside WSL.

  Edit (or create) =/etc/wsl.conf=:

  [interop]
  appendWindowsPath = false
  #+end_src
  Then, from PowerShell (outside WSL): =wsl --shutdown=, then reopen
  the Arch terminal.
  *Why:* the previous two steps fix the symptom for this shell/session
  by winning the PATH race; this instead removes Windows paths from
  WSL's PATH at the instance level, so nothing can shadow the nvm
  binaries again regardless of shell startup file ordering. Marked
  =*[you-run]*= since it edits root-owned system config and requires a
  full WSL restart — not something to change out from under you
  silently.

  *Caveat:* this also hides other Windows tools (git.exe, code.exe,
  etc.) from WSL shells — only do this if those aren't needed from
  within WSL, or re-add specific ones to PATH manually.

  *Skipped:* =/etc/wsl.conf= still has no =[interop]= block, but
  PATH ordering alone already resolves =npm=/=node= correctly, so
  this step turned out to be unnecessary.

* Quiz

1. =which nvm= reports "not found" even in a shell where =nvm= works
   fine interactively. Why doesn't that command prove nvm is broken?
2. =.bashrc= already sourced =nvm.sh= before this fix, yet =npm= still
   resolved to the Windows binary. Why didn't that alone fix it?
3. Both a Windows =npm.exe= (via WSL interop) and the WSL-managed
   =npm= exist on =PATH= at the same time. What actually decides which
   one =which npm= (and every other command) resolves to?
4. Setting =appendWindowsPath = false= in =wsl.conf= fixes this at the
   instance level instead of per-shell. What do you gain by doing it
   this way, and what do you give up?
5. A =npm install -g <pkg>= command succeeds with no errors, but
   =which <pkg's binary>= still can't find it afterward. What's the
   first thing you'd check, and why?

** Answer Key

1. =nvm= isn't a binary anywhere on disk — it's a shell function
   defined by *sourcing* =nvm.sh= into the current shell. =which= only
   searches =PATH= for executable files, so it can never find a shell
   function regardless of whether nvm is actually loaded and working.
2. WSL terminals start *login* shells, which read =~/.bash_profile=,
   not =~/.bashrc=, on startup. =.bashrc='s nvm-sourcing line never
   ran unless something in =.bash_profile= pulled it in — a fresh
   terminal never had nvm loaded in the first place, so it had nothing
   to do with =PATH= ordering yet.
3. =PATH= order. When multiple directories contain a same-named
   executable, the shell uses whichever one is found *first* while
   scanning =PATH= left to right — so the fix isn't "is the right npm
   installed," it's "does the WSL npm's directory appear before the
   =/mnt/c/...= interop directories."
4. Per-shell =PATH= reordering only fixes shells where it's applied
   and has to be redone if something re-introduces the Windows paths
   ahead of nvm's. =appendWindowsPath = false= removes Windows paths
   from WSL's =PATH= at the WSL-instance level, so no shell can ever
   have this problem again — at the cost of losing direct access to
   Windows executables (=code.exe=, =git.exe=, etc.) from within WSL
   unless re-added manually.
5. Whether the *npm prefix* the package installed into matches the
   npm/node currently active on =PATH= — a global install goes into
   whichever npm's configured prefix directory ran the install, and if
   that's the Windows npm (because =PATH= still resolved there when
   the install ran), the WSL shell will never see the new binary no
   matter how correct the install looked.
