#+TITLE: Give Arch bash an Ubuntu-like CLI theme
#+DATE: 2026-08-12

* Problem

Arch's default =/etc/bash.bashrc= / =~/.bashrc= ships a bare prompt and
no color defaults, unlike Ubuntu's which colorizes the prompt, =ls=,
and =grep= out of the box. Want the Arch WSL shell to feel similar.

* Quiz

1. Bash's default =PS1= shows no color at all until you add something
   specific to it. What exactly makes a prompt colored, and why does
   Arch's default lack it while Ubuntu's doesn't?
2. What two separate things does =dircolors= actually provide, and why
   does =ls --color=auto= alone do nothing without them?
3. You edit =~/.bashrc= in one terminal tab. A second, already-open
   tab still shows the old, uncolored prompt. Why?
4. =--color=auto= vs =--color=always= — what's the practical
   difference, and why does =auto= matter specifically when =ls='s
   output gets piped into another command?
5. A teammate installs this same config but their prompt still shows
   no color. What are the first two things you'd check, and why those
   specifically rather than assuming the =PS1= line itself is wrong?

** Answer Key

1. =PS1= has no ANSI escape codes in it by default — color only
   appears once =\033[...m= sequences are embedded directly in the
   =PS1= string itself. Ubuntu's default =bashrc= already sets a
   colorized =PS1=; Arch's ships a bare one.
2. =dircolors= supplies the =LS_COLORS= mapping (file type/extension →
   color code); =--color=auto= just tells =ls= to *consult* that
   mapping, and only when writing to a terminal. Without =LS_COLORS=
   set, there's no mapping to apply even with =--color=auto= on.
3. Bash only reads =.bashrc= (or =.bash_profile=) when a shell starts.
   Editing the file doesn't touch a shell that's already running and
   holds its own copy of =PS1= in memory — it has to be re-sourced or
   a new shell opened.
4. =auto= only emits color codes when stdout is an actual terminal
   (isatty); =always= emits them unconditionally. This matters because
   piping colored output (raw escape codes) into another command —
   =grep=, a file, a script — corrupts or confuses tools that expect
   plain text; =auto= avoids that by turning color off automatically
   once output isn't going to a terminal.
5. Whether =.bashrc= is actually being sourced at all for their shell
   type (login vs. interactive — see the WSL npm walkthrough for the
   same class of bug with =.bash_profile=), and whether =LS_COLORS= is
   actually exported in their environment. Assuming =PS1= itself is
   broken skips past the more common failure: the config exists but
   never gets loaded.
